# ネットワーク・インフラ基盤

### TCP / IP（Transmission Control Protocol / Internet Protocol／ティーシーピー／アイピー）
インターネット通信の基盤となる**世界共通の通信規格（プロトコル）**。<br>
TCPとIPをセットで「TCP/IP」と呼ぶことが多く、この規格があるおかげで**世界中のあらゆる機器が相互に通信できる**。<br>

**なぜ異なるメーカーの機器が通信できるのか:**<br>
- Apple製のiPhone、Samsung製のスマホ、Windows PC、Linuxサーバー、Cisco製ルーター...すべて違うメーカー・OS<br>
- しかし**TCP/IPという共通ルール**に従っているため、どの組み合わせでも通信できる<br>
- メーカーや機種が違っても「同じ言語（プロトコル）」で会話しているイメージ<br>

**TCPとIPの役割分担:**<br>

**IP（Internet Protocol）:**<br>
- **「どこに届けるか」を担当**（住所の役割）<br>
- データをパケット（小さな荷物）に分割して送る<br>
- IPアドレス（例: `192.168.1.1`）を使って宛先を指定<br>
- 配送の信頼性は保証しない（届かなくても知らない）<br>

**TCP（Transmission Control Protocol）:**<br>
- **「確実に届けるか」を担当**（信頼性の役割）<br>
- パケットが正しい順序で届くように管理<br>
- 欠けたパケットがあれば再送要求<br>
- 相手が受け取ったか確認しながら通信（確認応答）<br>

**郵便に例えると:**<br>
```
IP = 住所と郵便配達システム
  → 「東京都〇〇区...」という住所（IPアドレス）を使って荷物を配送
  → ただし、途中で紛失しても責任は持たない

TCP = 書留郵便の仕組み
  → 相手が受け取ったか確認
  → 届かなかったら再送
  → 複数の荷物が正しい順序で届くように管理
```

**TCPの主な特徴:**<br>

**① スリーウェイハンドシェイク（3ウェイハンドシェイク）**<br>
通信開始前に「接続確立」の手続きをする。信頼性の基盤。<br>
```
クライアント → サーバー: 「接続したいです」（SYN）
サーバー → クライアント: 「了解しました」（SYN-ACK）
クライアント → サーバー: 「ありがとう、開始します」（ACK）
→ この3回のやり取りで接続確立
```

**② データを分割して送信（パケット化）**<br>
大きなデータ（例: 1MBの画像）を小さなパケット（例: 1500バイト）に分割して送る。<br>
受信側で元のデータに復元する。<br>

**③ 順序制御**<br>
パケットの到着順序がバラバラでも、正しい順序に並び替えて復元。<br>
```
送信順: パケット1 → パケット2 → パケット3
到着順: パケット3 → パケット1 → パケット2（バラバラ）
TCP処理: パケット1 → パケット2 → パケット3（正しく復元）
```

**④ 再送制御**<br>
パケットが届かなかった場合、自動で再送。<br>

**⑤ フロー制御・輻輳制御**<br>
受信側の処理能力に合わせて送信速度を調整。ネットワークの混雑も考慮。<br>

**TCP/IPが使われている場面（ほぼすべて）:**<br>
- Webブラウジング（HTTP/HTTPS）<br>
- メール送受信（SMTP、IMAP）<br>
- ファイル転送（FTP、SFTP）<br>
- SSH接続<br>
- API通信<br>
- スマホアプリの通信<br>

**TCP/IPの歴史と普及:**<br>
- 1970年代にアメリカで開発された<br>
- **オープンな規格**として公開されたため、誰でも実装できた<br>
- 結果として世界標準になり、インターネットの基盤となった<br>
- WindowsもmacOSもLinuxもAndroidもiOSも、すべてTCP/IPで通信<br>

メールやWebページの表示でデータの欠落が起きないのも、世界中の異なるメーカーの機器が通信できるのも、すべてTCP/IPという共通規格のおかげ。<br>

### IPアドレス（アイピーアドレス）
TCP/IPの「IP」という通信規格があって、その規格の中で使う住所のようなものが「IPアドレス」。
パソコンやスマホ、ルータなどネットワークに接続する機器には必ずIPアドレスが割り当てられている。<br>
**パブリック（グローバル）IP**と**プライベートIP**の2種類がある。<br>

**パブリック（グローバル）IP:** インターネット上で使える世界で唯一のIPアドレス。<br>
例: `8.8.8.8`（Google DNS）、`203.0.113.1`など<br>
WEBサーバー、DBサーバー、APIサーバーなど、インターネットからアクセスされる機器が持つIPアドレス。<br>
一般的にはDBサーバーはプライベートIPを持ち、Webサーバー・APIサーバーを経由してアクセスされるのが通常のセキュリティ設計(クラウドDBサービス（AWS RDS、Azure SQLなど）では外部アクセス用にパブリックIPを持つこともある)

**プライベートIP:** 内部ネットワークでのみ使用。自由に設定可能で重複OK。<br>
スマホやPCが持つIPアドレスは通常プライベートIP。<br>
範囲: `192.168.x.x`、`10.x.x.x`、`172.16.x.x〜172.31.x.x`<br>
例: `192.168.1.100`（家庭内ルーター）、`10.0.0.5`（企業内サーバー）<br>

**見分け方:** 上記プライベートIP範囲以外はすべてパブリックIP。<br>

### SSH（Secure Shell／エスエスエイチ）
サーバーに安全にリモート接続するための暗号化技術とプロトコル。<br>
通信内容や認証情報が暗号化されるため、盗聴やなりすましのリスクが低くなる。<br>
自宅から会社サーバーにログインしてファイル操作やコマンド実行を行うときに使う。<br>

**認証方法は2種類:**<br>

**1. パスワード認証**<br>
ユーザー名とパスワードでログインする方式。<br>
シンプルだが、パスワードが漏洩したり総当たり攻撃（ブルートフォース）を受けるリスクがある。<br>
セキュリティ上の理由で無効化されていることも多い。<br>

**2. 公開鍵認証（推奨）**<br>
公開鍵と秘密鍵のペアを使って認証する方式。より安全。<br>
秘密鍵は自分のPCに保管し、公開鍵をサーバー側に登録する。<br>
秘密鍵がないと接続できないため、パスワードが漏れても安全。<br>
鍵のペアは暗号技術で紐づいているため、偽造がほぼ不可能。<br>

**仕組みのイメージ（公開鍵認証）:**<br>
```
 1. 自分のPCで鍵ペアを生成（ssh-keygenコマンド）
   → 秘密鍵（id_rsa）: 自分だけが持つ
   → 公開鍵（id_rsa.pub）: サーバーに配布してOK

2. サーバーに公開鍵を登録
   → サーバーの ~/.ssh/authorized_keys に公開鍵を追加

3. SSH接続時の認証
   → サーバーが公開鍵で暗号化したデータを送信
   → 自分のPCの秘密鍵でしか復号化できない
   → 復号化できれば本人確認完了＝接続OK
```

**実際の利用例:**<br>
- **GitHub**: 公開鍵認証を採用。GitHubアカウントに公開鍵を登録することで、`git push`や`git pull`が安全に実行できる<br>
- **AWSのEC2**: デフォルトで公開鍵認証。インスタンス作成時に鍵ペアをダウンロード<br>
- **社内サーバー**: セキュリティポリシーで公開鍵認証が必須の企業が多い<br>

**セキュリティのポイント:**<br>
- 秘密鍵は絶対に他人に渡さない（USBメモリでの持ち歩きも注意）<br>
- 秘密鍵にパスフレーズを設定するとさらに安全<br>
- 公開鍵は漏れても問題ない（名前の通り公開してOK）<br>

### LAN（Local Area Network）
ランと呼ぶ。限られた範囲（家庭やオフィス）内で接続されたコンピュータやデバイスのネットワークのこと。<br>高速な通信が可能で、リソースの共有（プリンタやファイルなど）が容易。<br>
家庭LANや社内LANなど表現することが多い。<br>
社内LANはインターネットから隔離されていることが多く、セキュリティが高い。<br>

### NAT / PAT（Network Address Translation / Port Address Translation／ナット／パット）
Network Address Translation（NAT）と Port Address Translation（PAT）。<br>
内部ネットワークのプライベートIPを外部のグローバルIPに変換してやり取りする仕組み。<br>
**現代のインターネット接続では、NATとPATはセットで使われるのが標準**で、家庭用ルーターや企業ルーターにほぼ必ず搭載されている。<br>
現代の企業向けファイアウォール製品は、ルーター機能も兼ねていることが多く、NAT/PAT機能も備えている。<br>

**NATとPATの違い:**<br>
- **NAT（狭義）**: IPアドレスだけを変換する仕組み。元々は1対1の変換を指す<br>
- **PAT（NAPT）**: IPアドレス**とポート番号**の両方を変換する仕組み。複数の内部端末が1つのグローバルIPを共有できる<br>

**現代の実情（重要）:**<br>
- 家庭用・企業用ルーターで「NAT」と呼ばれているものは、**ほぼすべてPAT（NAPT）**<br>
- 複数の端末が1つのグローバルIPでインターネット接続する = PAT<br>
- 単に「NAT」と言った場合、**PAT込みの意味で使われることが多い**<br>

**PATの仕組み（家庭での例）:**<br>
```
【家庭内の状況】
スマホ:   プライベートIP 192.168.1.10
PC:       プライベートIP 192.168.1.11
タブレット: プライベートIP 192.168.1.12
ルーター: グローバルIP 203.0.113.1（1つだけ）

【PATの動作】
1. スマホがGoogle（8.8.8.8:443）にアクセス
   送信元: 192.168.1.10:50001 → 宛先: 8.8.8.8:443

2. ルーターがPATで変換
   送信元: 203.0.113.1:10001 → 宛先: 8.8.8.8:443
   （内部のポート50001を外部のポート10001に対応付け）

3. PCもGoogle（8.8.8.8:443）にアクセス
   送信元: 192.168.1.11:50002 → 宛先: 8.8.8.8:443

4. ルーターがPATで変換
   送信元: 203.0.113.1:10002 → 宛先: 8.8.8.8:443
   （内部のポート50002を外部のポート10002に対応付け）

5. 返信が来たとき
   Googleからの返信: 203.0.113.1:10001 → ルーターが変換 → 192.168.1.10:50001（スマホ）
   Googleからの返信: 203.0.113.1:10002 → ルーターが変換 → 192.168.1.11:50002（PC）

ポイント: 同じグローバルIP（203.0.113.1）でも、ポート番号で端末を識別している
```

**1対1のNAT（スタティックNAT / ダイナミックNAT）:**<br>
**現代では特殊なケース**として扱われ、明示的に「スタティックNAT」「ダイナミックNAT」と呼ばれる。<br>

- **スタティックNAT（Static NAT）**: プライベートIPとグローバルIPを固定で1対1に紐付け<br>
  - 用途: 外部公開サーバー（Webサーバー、メールサーバー）に専用のグローバルIPを割り当てる<br>
  - 例: 社内サーバー（192.168.1.100）を固定でグローバルIP（203.0.113.50）に変換<br>

- **ダイナミックNAT（Dynamic NAT）**: 複数のグローバルIPプールから、接続時に1つを割り当て<br>
  - 用途: 企業で複数のグローバルIPを持っている場合に使われるが、PAT普及後はあまり使われない<br>

**現場での使い分け:**<br>
- **家庭・小規模オフィス**: PAT（1つのグローバルIPで複数端末が接続）← ほとんどこれ<br>
- **企業の外部公開サーバー**: スタティックNAT（固定のグローバルIPが必要）<br>
- **大規模企業の内部通信**: ダイナミックNAT（複数のグローバルIPプールを使う場合）<br>

**メリット:**<br>
- グローバルIPアドレスの節約（IPv4枯渇問題の緩和）<br>
- セキュリティ向上（内部ネットワーク構造を隠蔽）<br>
- 柔軟な内部ネットワーク設計が可能<br>

**用語の注意点:**<br>
- **NAT**: 広義では「PAT込み」の意味で使われることが多い<br>
- **PAT**: NAPTとも呼ばれる（Network Address Port Translation）<br>
- **IPマスカレード**: PATと同じ意味で使われる別称（特にLinux/Cisco環境）<br>

家でスマホ・PC・タブレットが同時にネットにつながるのも、会社で複数のPCが1つの回線を共有できるのも、すべてPATのおかげ。<br>

### レイヤーモデル（階層モデル）
ネットワーク通信を**階層（レイヤー）ごとに分割**して理解するための概念モデル。<br>
「**L4ロードバランサー**」「**L7ロードバランサー**」の「L4」「L7」は、このレイヤーモデルの層番号を指している。<br>

**代表的なモデル:**<br>
- **OSI参照モデル（7層）**: 理論的なモデル。教科書や資格試験で使われる<br>
- **TCP/IPモデル（4層）**: 実用的なモデル。実際のインターネットで使われる<br>

**各レイヤーの例（OSI参照モデル）:**<br>
- **L7（アプリケーション層）**: HTTP、FTP、SMTP、DNS<br>
- **L4（トランスポート層）**: TCP、UDP<br>
- **L3（ネットワーク層）**: IP、ルーター<br>
- **L2（データリンク層）**: Ethernet、Wi-Fi、スイッチ<br>
- **L1（物理層）**: LANケーブル、光ファイバー<br>

**なぜレイヤーに分けるのか:**<br>
複雑な通信を役割ごとに分業することで、独立して開発・改良できる。<br>
例: Wi-FiからLANケーブルに変えても、HTTPやTCPの仕組みは変える必要がない。<br>

**トラブルシューティングでの使い方:**<br>
「どのレイヤーの問題か」を切り分けることで、効率的に原因を特定できる。<br>
物理層（ケーブル）→ データリンク層（スイッチ）→ ネットワーク層（ルーター）→ トランスポート層（ポート）→ アプリケーション層（HTTP）の順に確認。<br>

詳細: [レイヤーモデル（階層モデル）](layer_model.md)<br>

### Internet Gateway（インターネットゲートウェイ）
内部ネットワーク（LAN）とインターネットをつなぐ「出入り口」の役割を果たす装置やサービス。<br>
オフィスビルの「正面玄関」のようなもので、内部と外部の通信を仲介する。<br>

**別の呼び方:** ルーター、ゲートウェイ、デフォルトゲートウェイ<br>

**何がInternet Gatewayにあたるか:**<br>
- **家庭**: Wi-Fiルーター（バッファロー、NECなど）<br>
- **企業**: 企業用ルーター、ファイアウォール<br>
- **クラウド**: AWS Internet Gateway、Azure vNet Gateway<br>

**主な機能:**<br>
- IPアドレス変換（プライベート ↔ パブリック）<br>
- 通信の振り分けとルーティング<br>
- セキュリティ制御（不正アクセスの防止）<br>

家でスマホがインターネットにつながるのも、会社のPCが外部サイトを見れるのも、すべてInternet Gatewayがあるから。<br>

### ロードバランサー（Load Balancer／LB）
複数のサーバーに負荷（トラフィック）を分散させる装置・サービス。<br>
アクセスが集中しても1台のサーバーだけに負荷が偏らないように、複数のサーバーに均等に振り分ける。<br>
「交通整理係」のようなもので、大量のアクセスを効率的にさばくために必須の仕組み。<br>

**主な役割:**<br>
- **負荷分散**: 複数のサーバーに均等にリクエストを振り分け<br>
- **可用性向上**: サーバーが1台ダウンしても、他のサーバーで継続稼働（フェイルオーバー）<br>
- **スケーラビリティ**: サーバーを追加するだけで処理能力を増やせる<br>
- **ヘルスチェック**: 各サーバーの稼働状況を監視し、異常があるサーバーには振り分けない<br>

**仕組みのイメージ:**<br>
```
ユーザー1 ──┐
ユーザー2 ──┤
ユーザー3 ──┼──→ ロードバランサー ──┬──→ Webサーバー1
ユーザー4 ──┤                       ├──→ Webサーバー2
ユーザー5 ──┘                       └──→ Webサーバー3

ロードバランサーが自動でサーバーを選んで振り分ける
全アクセスが1台に集中せず、3台で分散処理
```

**負荷分散のアルゴリズム（振り分け方法）:**<br>
- **ラウンドロビン（Round Robin）**: 順番に振り分け（サーバー1 → 2 → 3 → 1 → 2...）<br>
- **最小接続（Least Connection）**: 現在の接続数が最も少ないサーバーに振り分け<br>
- **IPハッシュ（IP Hash）**: クライアントのIPアドレスから計算して、同じ人は常に同じサーバーへ<br>
- **重み付けラウンドロビン（Weighted Round Robin）**: サーバーの性能差を考慮して振り分け比率を調整<br>

**ヘルスチェックの仕組み:**<br>
```
ロードバランサーが定期的に各サーバーに「生きてる？」と確認
例: 5秒ごとに HTTP GET / を送信

サーバー1: 200 OK → 正常、振り分け対象
サーバー2: タイムアウト → 異常、振り分け停止
サーバー3: 200 OK → 正常、振り分け対象

この場合、サーバー2には振り分けず、1と3だけで処理
サーバー2が復旧したら自動で振り分け再開
```

**種類:**<br>
- **L4ロードバランサー（レイヤー4）**: IPアドレスとポート番号で振り分け。トラフィックを管理するだけで、HTTPヘッダーなどの内容は見ない。高速だが柔軟性は低い<br>
- **L7ロードバランサー（レイヤー7）**: HTTPヘッダーやURLパスで振り分け。APIのルーティングや、特定のユーザーエージェントを別サーバーに振り分けるなど、細かい制御が可能。柔軟だが処理が重い<br>

**L7ロードバランサーの例:**<br>
```
example.com/api/*    → APIサーバー群
example.com/images/* → 画像サーバー群
example.com/*        → Webサーバー群

URLパスによって異なるサーバー群に振り分け可能
```
小〜中規模サイトの場合、L7も内部的にL4の機能を持っているため、L7ロードバランサーのみで十分なことが多いが、<br>
大規模・高トラフィックなサービスでは、L4とL7を組み合わせて使うことも多い。<br>
```
インターネット → L4ロードバランサー → L7ロードバランサー → サーバー群
```

**製品・サービス例:**<br>
- **ハードウェア型**: F5 BIG-IP、A10 Networks（企業向け、高価だが高性能）<br>
- **ソフトウェア型**: Nginx、HAProxy（無料、Linuxサーバーにインストール）<br>
- **クラウド型**: AWS Elastic Load Balancer（ELB/ALB/NLB）、Azure Load Balancer、Google Cloud Load Balancing<br>

**実務での使われ方:**<br>
```
【小規模サイト】
ロードバランサーなし、1台のサーバーで運用
→ アクセス少ないので問題なし

【中〜大規模サイト】
ロードバランサー + 複数のWebサーバー
→ アクセス増加に対応、サーバー障害時も継続稼働

【YouTube、Netflix級】
複数のロードバランサー + 数千台のサーバー
→ 世界中からの大量アクセスを分散処理
```

**セッション維持（スティッキーセッション）:**<br>
ショッピングカートなどで「同じユーザーは同じサーバーへ」振り分ける必要がある場合に使う。<br>
クッキーやIPアドレスで判断し、次回アクセス時も同じサーバーに接続させる。<br>

**クラウドでの具体例（AWS）:**<br>
```
1. EC2インスタンスを3台起動（Webサーバー）
2. Application Load Balancer（ALB）を作成
3. ALBに3台のEC2を登録（ターゲットグループ）
4. ALBのDNS名をドメインに設定
5. ユーザーからのアクセスをALBが3台に自動振り分け
```

**メリット:**<br>
- アクセス集中時もサーバーダウンしにくい<br>
- サーバー障害時も自動でフェイルオーバー<br>
- サーバー追加だけで簡単にスケールアウト可能<br>
- メンテナンス時も無停止でサーバー入れ替え<br>

Amazon、楽天、YouTubeなど、ほぼすべての大規模サービスがロードバランサーを使っている。<br>
アクセス数が増えてきたら「サーバーを強化する（スケールアップ）」より「サーバーを増やす（スケールアウト）+ ロードバランサー」が現代の定石。<br>

### ファイアウォール（Firewall）
ネットワーク通信を監視・制御してセキュリティを保つ仕組み。<br>
建物の「防火壁」が語源で、悪意ある通信をブロックして内部を守る。<br>

**ファイアウォールの定義:**<br>
以下の機能を持つものを「ファイアウォール」と呼ぶ：<br>
- 通信の許可・拒否を制御<br>
- 送信元・送信先・ポート番号での判断<br>
- ログ記録機能<br>

**商品・サービス例（各社が製造）:**<br>
- **家庭**: Wi-Fiルーター内蔵機能（バッファロー、ASUS、TP-Link）<br>
- **企業**: FortiGate（Fortinet）、SonicWall、Palo Alto（Palo Alto Networks）<br>
- **ソフトウェア**: Windows Defender ファイアウォール、iptables（Linux）<br>
- **クラウド**: AWS Security Groups、Azure Network Security Groups<br>

**種類:**<br>
- **ハードウェア型**: 専用機器（企業向け）<br>
- **ソフトウェア型**: PC・サーバーにインストール<br>
- **統合型**: ルーターに内蔵（家庭・小規模オフィス）<br>

「冷蔵庫」や「エアコン」と同じように、各社が独自製品を作っている技術分野。<br>
ちなみに家庭用ルーターのファイアウォール機能も製品によっては意外とできることが多い。<br>
例えば、子供のスマホやゲーム機を特定時間だけインターネット禁止にしたり、YouTubeなど特定サイトをブロックしたりできる。<br>

---

### FTP（File Transfer Protocol／エフティーピー）
昔からあるファイル転送プロトコル。<br>
サーバーとクライアント間でファイルをやり取りできるが、通信が暗号化されないためパスワードやデータが盗聴されやすい。<br>
現在は安全な代替手段が推奨される。<br>

**仕組み:**<br>
- **送信側**: FTPクライアント（FileZillaなど）でファイルを送信<br>
- **受信側**: OSにFTPサーバーソフト（vsftpd、ProFTPDなど）をインストールして受信環境を構築<br>

**設定に必要なもの:**<br>
- FTPサーバーソフトのインストール・設定<br>
- 送信側が接続するためのユーザーアカウント作成<br>
- ファイアウォール設定（ポート21の開放）<br>

古いWebホスティングでファイルをアップロードする際に使われていたが、セキュリティ上の問題で利用は減っている。<br>

---

### SFTP（SSH File Transfer Protocol／エスエフティーピー）
SSHを使ってファイルを暗号化して安全に転送するプロトコル。<br>
FTPの安全版と考えればよい。<br>
パスワードやファイル内容が暗号化されるため、現代ではこちらが推奨される。<br>
安全にサーバーへファイルをアップロードする際に使う。<br>

### DMZ（DeMilitarized Zone／ディーエムゼット／非武装地帯）
内部ネットワーク（社内LAN）と外部ネットワーク（インターネット）の間に設置される**中間的なネットワーク領域**。<br>
外部に公開する必要があるサーバー（Webサーバー、メールサーバーなど）を配置し、内部ネットワークを守る。<br>

**なぜDMZが必要か:**<br>
- 外部公開サーバーを社内LANに直接置くと、攻撃された際に社内全体が危険にさらされる<br>
- DMZに置けば、攻撃されても被害を限定できる（社内LANへの侵入を防ぐ）<br>

**DMZの構成イメージ:**<br>
```
インターネット
    ↓
ファイアウォール1
    ↓
  【DMZ】 ← 外部公開サーバー（Webサーバー、メールサーバー）
    ↓
ファイアウォール2
    ↓
社内LAN ← 重要な業務サーバー、PC（外部から直接アクセス不可）
```

**DMZに置かれるサーバー:**<br>
- Webサーバー（公開サイト）<br>
- メールサーバー（外部とメール送受信）<br>
- DNSサーバー（外部向け）<br>
- VPNゲートウェイ<br>

**DMZに置かない（社内LANに置く）サーバー:**<br>
- データベースサーバー（顧客情報など重要データ）<br>
- ファイルサーバー（社内文書）<br>
- 業務システムサーバー<br>

**セキュリティの考え方:**<br>
- DMZのサーバーは「攻撃される可能性がある」前提で運用<br>
- DMZから社内LANへの通信は厳しく制限<br>
- 二重のファイアウォールで多層防御（Defense in Depth）<br>

**現場での呼び方:**<br>
「WebサーバーはDMZに配置します」= 外部公開用の中間ネットワークに設置<br>
「DBサーバーは内部に置きます」= 社内LAN（DMZの内側）に設置<br>

軍事用語の「非武装地帯」から名付けられた、企業ネットワークの標準的なセキュリティ設計。<br>

### CDN（Content Delivery Network／コンテンツデリバリーネットワーク／シーディーエヌ）
世界中に分散配置されたサーバー群（エッジサーバー）を使って、Webコンテンツを高速に配信する仕組み。<br>
ユーザーに地理的に近いサーバーからコンテンツを配信することで、表示速度を大幅に向上させる。<br>

**誰がどう使うのか:**<br>
Webサイト・アプリの**運営者（サービス提供者）**が、CloudflareやAWS CloudFrontなどの**グローバルCDN企業**と契約する。<br>
CDN企業は世界中（東京、大阪、シンガポール、ニューヨーク、ロンドンなど）にエッジサーバーを持っている。<br>
契約すると、その世界中のサーバー網を使えるようになる。<br>

**重要なポイント:**<br>
- **日本のサービスでも、グローバルCDN企業と契約する**（日本だけのCDN企業を探す必要はない）<br>
- CloudflareやAWS CloudFrontは既に日本国内にもサーバーを持っている<br>
- 契約すると、自動的に世界中のサーバーが使える状態になる<br>
- ユーザーがアクセスすると、CDN側が自動で最寄りのサーバーから配信してくれる<br>

**具体例：日本の動画サイトを開発する場合**<br>
```
【準備】
1. 日本の運営者がAWS CloudFrontと契約（世界中のCDNサーバーが使える状態に）
2. 動画ファイルをAWS S3（オリジンサーバー）にアップロード
3. CloudFrontでCDN設定（「この動画はCDN経由で配信する」と指定）
4. CDN用のURL（例: https://d123abc.cloudfront.net/video.mp4）を取得
5. Webサイトの動画タグにCDN URLを埋め込む

【配信の流れ】
日本のユーザーAさんが動画を初めて再生
   → 東京のエッジサーバーにはまだファイルがない
   → エッジサーバーがS3（オリジン）から動画を取得してキャッシュ（コピー保存）
   → Aさんに配信（初回は少し時間がかかる）

日本のユーザーDさんが同じ動画を再生（Aさんの後）
   → 東京のエッジサーバーに既にキャッシュがある！
   → キャッシュから直接配信（オリジンにアクセス不要なので高速）

もし海外旅行中のユーザーBさんがアクセスしたら？
   → ニューヨークのエッジサーバーにはまだファイルがない
   → ニューヨークのエッジサーバーがS3から動画を取得してキャッシュ
   → Bさんに配信（ニューヨークでも初回アクセス時は少し時間がかかる）

アメリカのユーザーEさんが同じ動画を再生（Bさんの後）
   → ニューヨークのエッジサーバーに既にキャッシュがある
   → キャッシュから直接配信（オリジンにアクセス不要なので高速）
```

**重要：エッジサーバーへのファイル配置はオンデマンド**<br>
- 最初は**オリジンサーバー（S3など）にしかファイルがない**<br>
- ユーザーがアクセスした時に、その地域のエッジサーバーに**初めてキャッシュ**される<br>
- 全世界のエッジサーバーに事前配布されるわけではない<br>
- 人気のコンテンツは自然と多くのエッジサーバーにキャッシュされる<br>
- アクセスがない地域のエッジサーバーには配置されない（効率的）<br>

**サービス提供者がやること:**<br>
1. **CDNサービスと契約**（Cloudflare、AWS CloudFrontなど）<br>
2. **コンテンツをアップロード**（動画、画像など）<br>
3. **CDN URLを発行**（例: `https://cdn.example.com/video.mp4`）<br>
4. **WebサイトにCDN URLを埋め込む**<br>

**CDNサービスが自動でやってくれること:**<br>
- ユーザーの位置を判定<br>
- 最寄りのエッジサーバーを選択<br>
- ファイルをキャッシュして高速配信<br>
- 負荷分散とサーバー障害時の自動切り替え<br>

**仕組みのイメージ:**<br>
```
【CDNなし】
日本のユーザー → 遠いアメリカのサーバー → 遅い（500ms）

【CDNあり】
日本のユーザー → 近い東京のCDNサーバー → 速い（50ms）
アメリカのユーザー → 近いニューヨークのCDNサーバー → 速い（50ms）
```

**CDNで配信するもの:**<br>
- **静的ファイル**: 画像（.jpg、.png）、動画（.mp4）、CSS、JavaScript<br>
- **Webフォント**: Google Fontsなど<br>
- **ライブラリ**: jQuery、React などのJavaScriptライブラリ<br>
- **Webサイト全体**: HTML含めて全てキャッシュすることも可能<br>

**主要なCDNサービス（すべてグローバル企業）:**<br>
- **Cloudflare**（アメリカ）: 無料プランあり。世界300都市以上にサーバー。日本にも複数拠点<br>
- **AWS CloudFront**（アメリカ）: AWSのCDN。世界中に拠点。日本は東京・大阪にサーバーあり<br>
- **Akamai**（アメリカ）: 企業向けの老舗CDN。世界最大級のネットワーク。日本にも拠点多数<br>
- **Fastly**（アメリカ）: 開発者向けで柔軟なカスタマイズが可能。日本は東京にサーバー<br>
- **Azure CDN**（アメリカ）: Azure（マイクロソフト）のCDN。世界中に拠点。日本は東京・大阪にサーバーあり<br>
- **Google Cloud CDN**（アメリカ）: Google CloudのCDN。世界中に拠点。日本は東京にサーバー<br>

**メリット:**<br>
- **高速化**: ユーザーに近いサーバーから配信されるため表示が速い<br>
- **負荷分散**: 元サーバー（オリジンサーバー）の負荷を軽減<br>
- **可用性向上**: 一部のサーバーが落ちても他のサーバーで配信継続<br>
- **帯域節約**: 元サーバーの通信量を削減できる<br>

**実務での使い方:**<br>
```
1. 画像をS3にアップロード
2. CloudFrontでCDN設定
3. HTMLから画像を参照
   <img src="https://cdn.example.com/image.jpg">
4. ユーザーがアクセス
   → 最寄りのCDNサーバーが画像を配信（超高速）
```

**キャッシュの仕組み:**<br>
- 最初のアクセス時にオリジンサーバーからファイルを取得<br>
- CDNサーバーにファイルをキャッシュ（保存）<br>
- 2回目以降はキャッシュから直接配信（オリジンにアクセス不要）<br>
- TTL（Time To Live）で有効期限を設定可能<br>

**注意点:**<br>
- キャッシュされるため、ファイル更新時は「キャッシュクリア（パージ）」が必要<br>
- 動的コンテンツ（検索結果、ユーザーごとに変わるページ）はCDN向きではない<br>

YouTube、Netflix、大手ECサイトなど、ほぼ全ての大規模Webサービスが採用している現代のWeb高速化の必須技術。<br>
