# レイヤーモデル（階層モデル）

ネットワーク通信を**階層（レイヤー）ごとに分割**して理解・設計するための概念モデル。<br>
各レイヤーが特定の役割を持ち、上下のレイヤーと連携して通信を実現する。<br>

## なぜレイヤーに分けるのか？

**複雑な通信を分業して管理するため。**<br>

例えば、WebブラウザでWebページを表示するまでに：<br>
1. アプリケーション（ブラウザ）がHTTPリクエストを作る<br>
2. そのデータをTCPで信頼性のある形に整える<br>
3. さらにIPでパケット化して宛先を指定<br>
4. 最後にWi-FiやLANケーブルで物理的に送信<br>

このように**役割ごとに分けることで、それぞれ独立して開発・改良できる**。<br>
例えば、Wi-FiからLANケーブルに変えても、HTTPやTCPの仕組みは変える必要がない。<br>

---

## OSI参照モデル（7層モデル）

**国際標準化機構（ISO）が定義した理論的なモデル。**<br>
ネットワーク通信を7つの階層に分けて説明する。教科書やベンダー資格試験でよく使われる。<br>

| レイヤー | 名称 | 役割 | 具体例 |
|---------|------|------|--------|
| **第7層** | **アプリケーション層** | ユーザーが直接使うアプリケーション | HTTP、FTP、SMTP、DNS |
| **第6層** | **プレゼンテーション層** | データの形式変換・暗号化 | SSL/TLS、JPEG、文字コード変換 |
| **第5層** | **セッション層** | 通信の開始・維持・終了の管理 | NetBIOS、RPC |
| **第4層** | **トランスポート層** | 信頼性のあるデータ転送 | **TCP、UDP** |
| **第3層** | **ネットワーク層** | 異なるネットワーク間のルーティング | **IP、ルーター** |
| **第2層** | **データリンク層** | 同一ネットワーク内の通信 | Ethernet、Wi-Fi、スイッチ |
| **第1層** | **物理層** | 電気信号・光信号での伝送 | LANケーブル、光ファイバー |

**覚え方（上から）:**<br>
「**ア**プリ・**プ**レゼン・**セ**ッション・**ト**ランス・**ネ**ット・**デ**ータ・**ブ**ツ」<br>
→ 「**アプセトネデブ**」<br>

## TCP/IPモデル（4層モデル）

**実際のインターネットで使われている実用的なモデル。**<br>
OSI参照モデルよりシンプルで、現場ではこちらがよく使われる。<br>

| レイヤー | 名称 | OSI対応 | 役割 | 具体例 |
|---------|------|---------|------|--------|
| **第4層** | **アプリケーション層** | 第5〜7層 | アプリケーションとデータ形式 | HTTP、FTP、SMTP、DNS、SSL/TLS |
| **第3層** | **トランスポート層** | 第4層 | 信頼性のあるデータ転送 | **TCP、UDP** |
| **第2層** | **インターネット層** | 第3層 | ネットワーク間のルーティング | **IP** |
| **第1層** | **ネットワークインターフェース層** | 第1〜2層 | 物理的な通信 | Ethernet、Wi-Fi |

**OSI参照モデルとの違い:**<br>
- TCP/IPは**実装重視**で、実際の技術に即している<br>
- OSIは**理論重視**で、教育や概念理解に向いている<br>
- 実務では「TCP/IP」、資格試験では「OSI」が使われることが多い<br>

## レイヤーごとの詳細説明

### 第7層（アプリケーション層）

**ユーザーが直接操作するアプリケーションのレベル。**<br>

**役割:**<br>
- Webページの表示（HTTP/HTTPS）<br>
- メール送受信（SMTP、IMAP）<br>
- ファイル転送（FTP、SFTP）<br>
- ドメイン名解決（DNS）<br>

**具体例:**<br>
- ブラウザでURLを入力 → HTTPリクエスト送信<br>
- メールソフトでメール送信 → SMTPプロトコル使用<br>
- `ping google.com` → DNSで名前解決してからICMP送信<br>

**トラブルの例:**<br>
- 「Webページが表示されない」→ HTTP/HTTPSの問題<br>
- 「メールが送れない」→ SMTPの問題<br>

---

### 第4層（トランスポート層）

**データを確実に届けるための制御を行う。**<br>

**役割:**<br>
- データの分割と再構成<br>
- 順序制御と再送制御<br>
- ポート番号による宛先の識別<br>

**TCP（信頼性重視）:**<br>
- 確実にデータを届ける（再送制御あり）<br>
- 順序を保証<br>
- 用途: Web、メール、ファイル転送<br>

**UDP（速度重視）:**<br>
- データが届かなくても再送しない<br>
- 順序も保証しない<br>
- 用途: 動画ストリーミング、オンラインゲーム、VoIP<br>

**ポート番号の例:**<br>
```
Webサーバー: ポート80（HTTP）、443（HTTPS）
メールサーバー: ポート25（SMTP）、587（SMTP over TLS）
SSH: ポート22
```

**トラブルの例:**<br>
- 「接続が切れる」→ TCPの3ウェイハンドシェイク失敗<br>
- 「ファイアウォールでブロックされる」→ ポート番号の制限<br>

---

### 第3層（ネットワーク層）

**異なるネットワーク間でデータを届ける（ルーティング）。**<br>

**役割:**<br>
- IPアドレスで宛先を指定<br>
- パケットを最適な経路で転送<br>
- ルーターがこの層で動作<br>

**IP（Internet Protocol）の役割:**<br>
- 「どこに届けるか」を決める（住所の役割）<br>
- データをパケットに分割<br>
- ルーターがパケットを次のルーターへ転送<br>

**ルーティングの例:**<br>
```
東京のPC（192.168.1.10）→ インターネット → 大阪のサーバー（203.0.113.50）

経路: 東京PC → 家庭用ルーター → ISPルーター → 中継ルーター複数 → ISPルーター → 大阪サーバー
各ルーターが「次はどこに転送すればいいか」を判断（ルーティングテーブル使用）
```

**トラブルの例:**<br>
- 「サーバーに到達できない」→ ルーティングの問題<br>
- 「TTL exceeded」→ パケットがループしている<br>

---

### 第2層（データリンク層）

**同じネットワーク内での通信を管理。**<br>

**役割:**<br>
- MACアドレスで機器を識別<br>
- フレーム単位でデータを転送<br>
- スイッチ（L2スイッチ）がこの層で動作<br>

**MACアドレス:**<br>
- 機器固有の物理アドレス（例: `00:1A:2B:3C:4D:5E`）<br>
- ネットワークカードに書き込まれている<br>
- 同じLAN内でのやり取りに使用<br>

**EthernetとWi-Fi:**<br>
- どちらもデータリンク層のプロトコル<br>
- Ethernet: LANケーブルで有線接続<br>
- Wi-Fi: 無線で接続<br>

**トラブルの例:**<br>
- 「同じネットワーク内で通信できない」→ スイッチやMACアドレスの問題<br>
- 「IPアドレスの重複」→ ARPテーブルの混乱<br>

---

### 第1層（物理層）

**電気信号や光信号で実際にデータを送る。**<br>

**役割:**<br>
- ビット列を物理的な信号に変換<br>
- ケーブルの規格や電圧を定義<br>
- ハブ（物理的な中継器）がこの層で動作<br>

**具体例:**<br>
- LANケーブル（Cat5e、Cat6、Cat7）<br>
- 光ファイバーケーブル<br>
- Wi-Fi電波（2.4GHz、5GHz）<br>
- USB、HDMI<br>

**トラブルの例:**<br>
- 「LANケーブルが断線」→ 物理的な接続問題<br>
- 「ケーブルが規格外で速度が出ない」→ Cat5ケーブルでギガビット通信不可<br>

## レイヤーと実際の技術の対応

### ロードバランサー
- **L4ロードバランサー** = トランスポート層（第4層）で動作<br>
  → IPアドレス + ポート番号で振り分け<br>
  → 高速だが柔軟性は低い<br>

- **L7ロードバランサー** = アプリケーション層（第7層）で動作<br>
  → HTTPヘッダーやURLパスで振り分け<br>
  → 柔軟だが処理が重い<br>

### ファイアウォール
- **L3ファイアウォール** = ネットワーク層で動作<br>
  → IPアドレスで通信を制御<br>

- **L4ファイアウォール** = トランスポート層で動作<br>
  → IPアドレス + ポート番号で制御<br>

- **L7ファイアウォール（WAF）** = アプリケーション層で動作<br>
  → HTTPリクエストの内容を検査してSQLインジェクションなどを防ぐ<br>

### スイッチ
- **L2スイッチ** = データリンク層で動作<br>
  → MACアドレスで転送先を決定<br>

- **L3スイッチ** = ネットワーク層で動作<br>
  → IPアドレスでルーティング（ルーター機能を持つスイッチ）<br>

## 実際の通信の流れ（例：Webページ閲覧）

```
【送信側（クライアントPC）】
第7層: ブラウザが「https://example.com/index.html」へのHTTPリクエストを作成
第6層: SSL/TLSで暗号化
第5層: セッション確立
第4層: TCPでポート443を指定、データを分割
第3層: IPアドレス「203.0.113.50」へのパケット作成
第2層: ルーターのMACアドレスを指定してフレーム作成
第1層: LANケーブルで電気信号として送信
      ↓
【ネットワーク経路】
ルーター複数台を経由（第3層のIPアドレスで転送）
      ↓
【受信側（Webサーバー）】
第1層: 電気信号を受信
第2層: フレームを受信してMACアドレス確認
第3層: パケットを受信してIPアドレス確認
第4層: TCPで再構成、ポート443で待ち受けているプロセスへ
第5層: セッション維持
第6層: SSL/TLSで復号化
第7層: WebサーバーソフトがHTTPリクエストを解釈してHTMLを返す
```

受信したら逆順でクライアントPCに返す。この往復がすべて自動で行われている。<br>

## カプセル化（Encapsulation）

**上の層から順番にヘッダーを付け足していく仕組み。**<br>

```
アプリケーション層: 「HTTPリクエスト」
      ↓（TCPヘッダー追加）
トランスポート層: [TCPヘッダー | HTTPリクエスト]
      ↓（IPヘッダー追加）
ネットワーク層: [IPヘッダー | TCPヘッダー | HTTPリクエスト]
      ↓（Ethernetヘッダー追加）
データリンク層: [Ethernetヘッダー | IPヘッダー | TCPヘッダー | HTTPリクエスト | トレーラー]
```

受信側ではヘッダーを1つずつ剥がしていく（デカプセル化）。<br>
各層が独立して動作できるのは、このカプセル化の仕組みのおかげ。<br>

## レイヤーモデルを理解するメリット

### トラブルシューティングが効率的になる
「どのレイヤーの問題か」を切り分けられる。<br>

```
【問題】Webページが表示されない

第1層: LANケーブルは刺さっているか？ → OK
第2層: 同じLAN内の機器と通信できるか？（pingでMACアドレス確認）→ OK
第3層: ルーターまで通信できるか？（pingでIPアドレス確認）→ OK
第4層: ポート80/443は開いているか？（telnetやnc確認）→ NG！
→ ファイアウォールでポートがブロックされていることが判明
```

### 技術の理解が深まる
「L4ロードバランサー」「L3スイッチ」など、レイヤーを指定した用語の意味がわかる。<br>

### ネットワーク設計がしやすくなる
どのレイヤーで負荷分散やセキュリティ対策をするかを判断できる。<br>

## まとめ

**OSI参照モデル（7層）:**<br>
理論的なモデル。教科書や資格試験で使われる。各層の役割が細かく分かれている。<br>

**TCP/IPモデル（4層）:**<br>
実用的なモデル。実際のインターネットで使われる。現場ではこちらがメイン。<br>

**各層の独立性:**<br>
下の層（物理層）を変えても、上の層（アプリケーション層）は影響を受けない。<br>
だからWi-FiでもLANケーブルでも、同じWebブラウザが使える。<br>

**「L4」「L7」などの意味:**<br>
ロードバランサーやファイアウォールで使われる「L4」「L7」などは、このレイヤーモデルの層を指している。<br>
どの層で処理するかで、できることと性能が変わる。<br>

レイヤーモデルはネットワークの基礎中の基礎。これを理解すると、あらゆるネットワーク技術が理解しやすくなる。<br>

## おまけ：企業で一般的なネットワーク構成例

実際の企業で採用されている代表的なネットワーク構成を、オンプレミス（自社運用）とクラウド利用の2パターンで紹介。<br>

### 【パターン1】中小企業のオンプレミス構成（統合型ファイアウォール使用）

**特徴:** ルーター・ファイアウォール・VPN機能が1台に統合された機器を使用。コスト効率が良く、管理もシンプル。<br>

```
                      インターネット
                           |
                           |
                  [ISP提供ルーター]
                   (光回線終端装置)
                           |
                           |
        ┌──────────────────────────────────┐
        │  統合型ファイアウォール/ルーター   │ ← NAT/PAT実行（L3/L4）
        │  (FortiGate, Palo Alto, etc.)    │    グローバルIP: 1個
        │                                   │    セキュリティ制御
        └──────────────────────────────────┘
                           |
           ┌───────────────┼───────────────┐
           |               |               |
    ┌─────▼──────┐  ┌────▼──────┐  ┌────▼──────┐
    │    DMZ      │  │  社内LAN   │  │ VPN接続  │
    │ (Public側)  │  │ (Private)  │  │ (在宅等)  │
    └─────┬──────┘  └────┬──────┘  └───────────┘
          |               |
   ┌──────┴──────┐   ┌───┴─────────┐
   |             |   |               |
┌──▼──┐    ┌───▼──┐ ┌──▼────┐  ┌───▼────┐
│ Web │    │Mail  │ │ L2/L3 │  │  AD    │
│Server│   │Server│ │Switch │  │Server  │
└──┬──┘    └──────┘ └───┬───┘  └────────┘
   |                    |
   |              ┌─────┴─────────────┐
   |              |                   |
   |          ┌───▼────┐        ┌────▼────┐
   |          │業務用PC│        │  DB     │
   |          │(50台)  │        │ Server  │
   |          └────────┘        └─────────┘
   |
   └──────────[インターネット公開]


【レイヤー構成】
統合型ファイアウォール: L3（ルーティング）+ L4（ポート制御）
DMZサーバー: L7（アプリケーション）
L2/L3スイッチ: L2（MACアドレス）+ L3（VLAN間ルーティング）

【IPアドレス設計例】
- DMZ: 10.0.1.0/24 (Webサーバー: 10.0.1.10, メールサーバー: 10.0.1.20)
- 社内LAN: 192.168.1.0/24 (PC群: 192.168.1.100~150, DBサーバー: 192.168.1.200)
- グローバルIP: 203.0.113.50（1個）← すべての通信がここでNAT/PAT変換
```

**メリット:**<br>
- 初期コストが比較的安い（機器1台）<br>
- 管理がシンプル（設定箇所が集約）<br>
- 小〜中規模に最適<br>

**デメリット:**<br>
- 1台に集中するため単一障害点（SPOF）<br>
- トラフィック増加時のスケールが困難<br>

### 【パターン2】AWS使用の現代的なクラウド構成（マイクロサービス型）

**特徴:** インフラをAWSに移行し、スケーラビリティと可用性を重視。複数の可用性ゾーン（AZ）で冗長化。<br>

```
                      インターネット
                           |
                           |
            ┌──────────────▼──────────────┐
            │   Route 53 (DNS)            │ ← L7（DNS）
            │   グローバルロードバランシング│
            └──────────────┬──────────────┘
                           |
            ┌──────────────▼──────────────┐
            │   CloudFront (CDN)          │ ← L7（キャッシュ）
            │   エッジロケーション (世界中) │
            └──────────────┬──────────────┘
                           |
            ┌──────────────▼──────────────┐
            │   AWS WAF                   │ ← L7（ファイアウォール）
            │   (Web Application FW)      │
            └──────────────┬──────────────┘
                           |
            ┌──────────────▼──────────────┐
            │  Internet Gateway           │ ← NAT機能（グローバルIP提供）
            └──────────────┬──────────────┘
                           |
        ═══════════════════╪═══════════════════════
        ║   VPC (Virtual Private Cloud)         ║
        ║   (例: 10.0.0.0/16)                   ║
        ═══════════════════╪═══════════════════════
                           |
           ┌───────────────┼───────────────┐
           |               |               |
    ┌──────▼──────────────▼──────────────▼──────┐
    │    Network ACL (Subnet レベル)            │ ← L4（ステートレス）
    │    セキュリティグループ (Instance レベル) │ ← L4（ステートフル）
    └──────┬──────────────┬──────────────┬──────┘
           |               |               |
    ┌──────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐
    │ Public Subnet│ │Public Subnet│ │Private Sub │
    │  (AZ-1a)     │ │  (AZ-1c)    │ │  (AZ-1a)   │
    │ 10.0.1.0/24  │ │10.0.2.0/24  │ │10.0.10.0/24│
    └──────┬──────┘ └─────┬──────┘ └─────┬──────┘
           |               |               |
    ┌──────▼───────────────▼──────┐       |
    │  ALB (Application LB)       │ ← L7（URLルーティング）
    │  (複数AZで冗長化)            │
    └──────┬───────────────┬──────┘
           |               |
    ┌──────▼──────┐ ┌─────▼──────┐
    │   ECS/EC2   │ │   ECS/EC2  │ ← Webアプリケーション
    │  (AZ-1a)    │ │  (AZ-1c)   │    Auto Scaling対応
    │ Web/APIサーバー│ │Web/APIサーバー│
    └──────┬──────┘ └─────┬──────┘
           |               |
           └───────┬───────┘
                   |
        ┌──────────▼──────────┐
        │  Private Subnet      │
        │  (AZ-1a + AZ-1c)     │ ← DBは外部非公開
        └──────────┬───────────┘
                   |
        ┌──────────▼──────────┐
        │  RDS (PostgreSQL)    │ ← データベース
        │  Multi-AZ有効        │    自動フェイルオーバー
        │  (Primary + Standby) │
        └──────────────────────┘


【社内からのアクセス】
社内オフィス → VPN Gateway → Private Subnet → 管理コンソール

【その他のAWSサービス】
- S3: 静的ファイル（画像・動画）保存
- Lambda: サーバーレス処理
- ElastiCache: Redis/Memcachedキャッシュ
- CloudWatch: 監視・ログ集約


【レイヤー構成】
CloudFront/WAF: L7（アプリケーション層）
ALB: L7（HTTPヘッダー・URLパス処理）
NLB（使用する場合）: L4（TCP/UDP）
Security Group/Network ACL: L4（ポート制御）
Internet Gateway: L3（IPルーティング）

【IPアドレス設計例】
- VPC: 10.0.0.0/16
- Public Subnet (AZ-1a): 10.0.1.0/24
- Public Subnet (AZ-1c): 10.0.2.0/24
- Private Subnet (AZ-1a): 10.0.10.0/24
- Private Subnet (AZ-1c): 10.0.11.0/24
- DB Subnet (AZ-1a): 10.0.20.0/24
- DB Subnet (AZ-1c): 10.0.21.0/24
```

**メリット:**<br>
- 高可用性（複数AZで冗長化、1つのAZが落ちても継続稼働）<br>
- 自動スケーリング（アクセス増加時にサーバー自動追加）<br>
- 運用負荷が低い（インフラ管理をAWSに委任）<br>
- グローバル配信が容易（CloudFrontが世界中にエッジサーバー）<br>
- 従量課金（使った分だけ支払い）<br>

**デメリット:**<br>
- 長期的なコストが高くなる可能性<br>
- AWS特有の知識が必要<br>
- ベンダーロックインのリスク<br>

### 構成選択の目安

**オンプレミス統合型（パターン1）が向いている企業:**<br>
- 従業員50〜500名程度の中小企業<br>
- 予算が限られている<br>
- 既存のオンプレミス資産がある<br>
- データを自社で管理したい（規制・コンプライアンス）<br>

**AWSフルクラウド（パターン2）が向いている企業:**<br>
- スタートアップ・ベンチャー<br>
- 急速な成長が見込まれる<br>
- グローバル展開を考えている<br>
- インフラ管理の人員が限られている<br>
- トラフィックの変動が大きい（イベント系サービスなど）<br>

**ハイブリッド構成（パターン3）が向いている企業:**<br>
- 従業員1000名以上の大企業<br>
- 既存の基幹システム資産が大きい<br>
- 段階的にクラウド移行したい<br>
- データのガバナンスが厳格<br>

現代の企業は「パターン2（AWSフルクラウド）」か「パターン3（ハイブリッド）」を選択することが多い。<br>
特にスタートアップや新規事業は最初からクラウドネイティブで構築するのが主流。<br>
