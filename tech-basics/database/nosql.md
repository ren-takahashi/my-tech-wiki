# NoSQL（Not Only SQL）

**RDB（リレーショナルデータベース）以外のデータベースの総称。**<br>
「SQLを使わない」という意味ではなく、「SQLだけじゃない」（Not Only SQL）という意味。<br>
テーブル・行・列の固定的な構造を持たず、より柔軟なデータモデルで大量データや高速アクセスに対応する。<br>

## なぜNoSQLが生まれたのか？

**背景: RDBだけでは対応できない課題が増えた**<br>

### RDBの限界（2000年代後半〜）
1. **スケールアウトが困難**<br>
   - RDBは1台の高性能サーバー（スケールアップ）が基本<br>
   - 複数サーバーに分散（スケールアウト）するのが苦手<br>
   - Twitter、Facebookなど数億ユーザー規模では限界に<br>

2. **スキーマ変更のコストが高い**<br>
   - テーブル構造を事前に厳密に定義する必要がある<br>
   - 後からカラム追加などの変更が大変<br>
   - 柔軟なデータ構造が要求されるアプリには不向き<br>

3. **JOIN処理が重い**<br>
   - 正規化してテーブルを分割すると、クエリでJOINが必要<br>
   - データ量が増えるとJOINのコストが跳ね上がる<br>

**NoSQLの登場:**<br>
これらの課題を解決するため、特定の用途に特化したデータベースが登場。<br>
Google（BigTable）、Amazon（Dynamo）などが社内向けに開発し、その思想がオープンソース化された。<br>

---

## RDBとNoSQLの違い（重要）

| 項目 | RDB（リレーショナルDB） | NoSQL |
|------|------------------------|-------|
| **データモデル** | テーブル（行と列） | 多様（KVS、ドキュメント、グラフなど） |
| **スキーマ** | 固定（事前定義が必須） | 柔軟（動的に変更可能） |
| **スケーラビリティ** | スケールアップ（垂直） | スケールアウト（水平） |
| **トランザクション** | ACID保証（強い整合性） | BASE（結果整合性） |
| **JOIN** | 得意（複数テーブル結合） | 基本的に不得意（非正規化） |
| **クエリ言語** | SQL（標準化されている） | 製品ごとに異なる |
| **適している用途** | 業務システム、金融、EC | SNS、IoT、ログ、キャッシュ |

**ACID vs BASE:**<br>
- **ACID（RDB）**: Atomicity（原子性）、Consistency（一貫性）、Isolation（独立性）、Durability（永続性）<br>
  → 銀行の送金処理など、絶対に整合性を保つ必要がある場合<br>

- **BASE（NoSQL）**: Basically Available（基本的に利用可能）、Soft state（柔軟な状態）、Eventually consistent（結果整合性）<br>
  → SNSの「いいね」数など、多少のズレが許容される場合<br>

## NoSQLの4つの主要タイプ

### 1. キーバリューストア（Key-Value Store / KVS）

**最もシンプルな形式。キー（key）と値（value）のペアでデータを保存。**<br>

**仕組み:**<br>
```
キー       :  値
"user:1001" → "{"name": "田中太郎", "age": 30}"
"session:abc123" → "{"user_id": 1001, "login_at": "2024-01-01"}"
"cache:top_news" → "[ニュース一覧のJSON]"
```

キーを指定すれば一瞬で値を取得できる（O(1)の速度）。<br>
内部的にはハッシュマップのような構造。<br>

**特徴:**<br>
- **超高速**（キーでの取得が1ms以下）<br>
- **シンプル**（複雑なクエリは不可能）<br>
- **メモリベース**が多い（揮発性だが超高速）<br>

**代表的な製品:**<br>
- **Redis**: メモリベース、キャッシュで最も人気<br>
- **Memcached**: シンプルなキャッシュ専用<br>
- **Amazon DynamoDB**: AWS提供、永続化対応<br>

**使われる場面:**<br>
```
【ユースケース】
1. セッション管理
   ユーザーのログイン状態をRedisに保存
   → Webサーバーが複数台あってもセッション共有できる

2. キャッシュ
   DBから取得した結果をRedisにキャッシュ
   → 2回目以降は高速レスポンス（DBへの問い合わせ不要）

3. リアルタイムランキング
   ゲームのスコアランキングをRedisで管理
   → ソート済みセット機能で高速ランキング取得

4. レート制限
   "api:user:1001:requests" → カウンターで回数制限
   → 1分間に100回までのAPI制限などを実装
```

**実例:**<br>
```
# Redisでセッション管理
SET session:abc123 '{"user_id": 1001, "role": "admin"}' EX 3600
# ↑ キーsession:abc123に値を保存、3600秒（1時間）で自動削除

GET session:abc123
# ↑ セッション情報を即座に取得
```

### 2. ドキュメント指向データベース（Document Store）

**JSON/XMLのような「ドキュメント」でデータを保存。階層構造を持てる。**<br>

**仕組み:**<br>
```json
// ユーザードキュメント（1つのJSONが1レコード）
{
  "_id": "user001",
  "name": "田中太郎",
  "age": 30,
  "email": "tanaka@example.com",
  "address": {
    "zip": "100-0001",
    "city": "東京都千代田区"
  },
  "hobbies": ["読書", "旅行", "プログラミング"],
  "created_at": "2024-01-01T10:00:00Z"
}
```

**特徴:**<br>
- **スキーマレス**: ドキュメントごとに異なる構造でOK<br>
- **ネスト構造**: オブジェクトや配列を含められる<br>
- **柔軟なクエリ**: 条件検索やソートが可能（KVSより高機能）<br>

**代表的な製品:**<br>
- **MongoDB**: 最も人気のあるドキュメントDB<br>
- **Amazon DynamoDB**: KVSとドキュメントのハイブリッド<br>
- **Couchbase**: モバイルアプリとの同期が得意<br>
- **Firestore（Firebase）**: Googleのモバイル向けDB<br>

**使われる場面:**<br>
```
【ユースケース】
1. コンテンツ管理システム（CMS）
   ブログ記事、商品情報など、構造が柔軟なコンテンツ
   記事Aは「タグ」フィールドあり、記事Bはなし、でもOK

2. ユーザープロフィール
   ユーザーごとに持つ情報が違う（趣味、職歴など）
   RDBだと大量の列が必要 → MongoDBなら柔軟に対応

3. IoTデータ保存
   センサーデータをJSON形式でどんどん保存
   後から分析しやすい

4. カタログ・商品DB
   ECサイトの商品情報（カテゴリごとに属性が違う）
   家電 → サイズ、消費電力
   本 → 著者、ISBN、ページ数
```

**実例（MongoDB）:**<br>
```javascript
// ユーザー検索（年齢が25歳以上30歳以下）
db.users.find({ age: { $gte: 25, $lte: 30 } })

// ネストしたフィールドでの検索
db.users.find({ "address.city": "東京都千代田区" })

// 配列の中身で検索
db.users.find({ hobbies: "プログラミング" })
```

**RDBとの比較:**<br>
```
【RDBの場合】
usersテーブル、addressesテーブル、hobbiesテーブルに分割
→ JOIN必要（3テーブル結合）、スキーマ変更が大変

【MongoDBの場合】
1つのドキュメントに全部入れる
→ JOINなし、1回のクエリで全データ取得、スキーマ変更は自由
```

### 3. カラム指向データベース（Column-Family Store）

**行ではなく「列」単位でデータを保存。大量データの集計・分析に強い。**<br>

**RDB（行指向）との違い:**<br>
```
【RDB（行指向）】ディスクに行単位で保存
行1: ID=1, 名前=田中, 年齢=30, 住所=東京
行2: ID=2, 名前=佐藤, 年齢=25, 住所=大阪
行3: ID=3, 名前=鈴木, 年齢=35, 住所=福岡

「年齢の平均を計算したい」
→ 全行を読み込んで、各行から年齢カラムを抽出（無駄が多い）

【カラム指向】ディスクに列単位で保存
ID列: [1, 2, 3]
名前列: [田中, 佐藤, 鈴木]
年齢列: [30, 25, 35] ← この列だけ読めばOK！
住所列: [東京, 大阪, 福岡]

「年齢の平均を計算したい」
→ 年齢列だけを読み込めば良い（超高速）
```

**特徴:**<br>
- **集計クエリが超高速**（列単位で圧縮・読み込み）<br>
- **水平分散が得意**（ペタバイト級のデータを複数サーバーに分散）<br>
- **書き込みは普通**（集計特化型）<br>

**代表的な製品:**<br>
- **Apache Cassandra**: 分散に強い、Netflixなどが使用<br>
- **Apache HBase**: Hadoopエコシステムの一部<br>
- **Amazon Redshift**: AWS提供のデータウェアハウス<br>
- **Google BigQuery**: Googleのビッグデータ分析サービス<br>

**使われる場面:**<br>
```
【ユースケース】
1. アクセスログの分析
   数億件のアクセスログから「地域別のPV数」を集計
   → 「地域」列だけを読んで超高速集計

2. IoTセンサーデータの分析
   数千台のセンサーから毎秒データが届く
   → 分散保存して、後から集計分析

3. 時系列データ
   株価、気温、トラフィックなど時系列のデータ保存と分析
   → 特定期間の平均・最大・最小を高速計算

4. データウェアハウス
   業務システムのデータを集約して経営分析
   → 売上推移、顧客分析など
```

**実例（Cassandra）:**<br>
```sql
-- Netflixがユーザーの視聴履歴を保存する例
CREATE TABLE viewing_history (
  user_id UUID,
  video_id UUID,
  watched_at TIMESTAMP,
  duration INT,
  PRIMARY KEY (user_id, watched_at)
);

-- 特定ユーザーの視聴履歴を取得
SELECT * FROM viewing_history WHERE user_id = 'abc-123';
```

**いつ使うべきか:**<br>
- 読み込み（集計）が多く、書き込みは少ない<br>
- データ量がテラバイト〜ペタバイト級<br>
- リアルタイム性よりも分析精度を重視<br>

### 4. グラフデータベース（Graph Database）

**ノード（点）とエッジ（線）でデータの関係性を保存。SNS、推薦システムに最適。**<br>

**仕組み:**<br>
```
[田中] --友達--> [佐藤]
  |                 |
 勤務              勤務
  |                 |
  ▼                 ▼
[A社] --------取引-------- [B社]

ノード: 田中、佐藤、A社、B社
エッジ: 友達、勤務、取引
```

RDBで「友達の友達」を探すと複雑なJOINが必要だが、グラフDBなら即座に辿れる。<br>

**特徴:**<br>
- **関係性の探索が超高速**（数ホップ先まで即座に探索）<br>
- **柔軟な関係性**（ノード追加・関係追加が容易）<br>
- **直感的なクエリ**（グラフ構造そのままにクエリを書ける）<br>

**代表的な製品:**<br>
- **Neo4j**: 最も人気のあるグラフDB<br>
- **Amazon Neptune**: AWS提供のグラフDB<br>
- **ArangoDB**: マルチモデル（ドキュメント+グラフ）<br>

**使われる場面:**<br>
```
【ユースケース】
1. SNSの友達ネットワーク
   「友達の友達を探す」
   「共通の友達を見つける」
   → RDBだと複雑なJOIN、グラフDBなら一瞬

2. 推薦システム
   「この商品を買った人は、こんな商品も買っています」
   購入履歴のつながりから推薦商品を探す

3. 不正検出
   銀行口座間の送金ネットワークを分析
   → マネーロンダリングのパターンを検出

4. ナレッジグラフ
   Wikipediaのような知識の関連性を保存
   「AとBはどう繋がっているか？」を探索

5. 組織図・権限管理
   従業員の上下関係、部署の階層構造を管理
```

**実例（Neo4j / Cypherクエリ）:**<br>
```cypher
// 田中さんの友達の友達を探す
MATCH (tanaka:Person {name: '田中'})-[:FRIEND]->(friend)-[:FRIEND]->(fof)
RETURN fof.name

// 共通の友達を見つける
MATCH (tanaka:Person {name: '田中'})-[:FRIEND]->(common)<-[:FRIEND]-(sato:Person {name: '佐藤'})
RETURN common.name

// 最短経路を探す（6次の隔たり問題）
MATCH path = shortestPath((start:Person {name: '田中'})-[:FRIEND*]-(end:Person {name: 'ビル・ゲイツ'}))
RETURN path
```

**RDBとの比較:**<br>
```
【RDBの場合】
usersテーブル、friendshipsテーブル（多対多の中間テーブル）
「友達の友達」を探すには自己JOINが必要
→ 3ホップ、4ホップと増えるとクエリが複雑化、遅くなる

【グラフDBの場合】
ノードとエッジで直接関係を表現
→ 何ホップ先でも高速に探索可能
```

## NoSQLを使うべきタイミング（重要）

### NoSQLが向いている場合

**1. スケールアウトが必要**<br>
- ユーザー数が数百万〜数億人規模<br>
- データ量がテラバイト〜ペタバイト<br>
- 1台のサーバーでは処理しきれない<br>
例: Twitter、Facebook、Instagram<br>

**2. スキーマが流動的**<br>
- サービス初期で仕様が固まっていない<br>
- ユーザーごとにデータ構造が違う<br>
- 頻繁にカラム追加・変更が発生する<br>
例: スタートアップのMVP開発、CMSシステム<br>

**3. 高速な読み書きが必要**<br>
- キャッシュ、セッション管理<br>
- リアルタイムランキング<br>
- IoTセンサーデータの大量書き込み<br>
例: ゲームのランキング、センサーデータ収集<br>

**4. 関係性の探索が中心**<br>
- SNSの友達ネットワーク<br>
- 推薦システム<br>
- 不正検出<br>
例: LinkedIn、Netflix推薦、金融機関の不正検出<br>

**5. JOINが不要（非正規化でOK）**<br>
- データが独立している<br>
- 読み込み性能を最優先<br>
例: ログデータ、イベントデータ<br>

---

### RDBが向いている場合（NoSQLを使うべきでない）

**1. トランザクションの整合性が絶対に必要**<br>
- 金融システム（銀行、証券）<br>
- ECサイトの在庫管理・決済<br>
- 会計システム<br>
→ ACID保証が必須なのでRDB一択<br>

**2. 複雑なクエリ・集計が多い**<br>
- 複数テーブルを結合した分析<br>
- GROUP BY、サブクエリを使った複雑な集計<br>
- アドホックなレポート生成<br>
→ SQLの表現力が必要<br>

**3. データ構造が固定されている**<br>
- 業務システム（人事、経理）<br>
- 既存の基幹システム<br>
→ スキーマが決まっているならRDBの方が安全<br>

**4. データ量がそこまで大きくない**<br>
- 数百GB以下<br>
- 1台のサーバーで十分処理できる<br>
→ わざわざNoSQLを使う必要がない<br>

## 実務での使い分け（ハイブリッド構成）

**現代のシステムは「RDB + NoSQL」を組み合わせるのが主流。**<br>

### 典型的なWebサービスの構成例

```
【ECサイトの例】

RDB (PostgreSQL / MySQL)
- ユーザーマスター（ID、メアド、パスワードハッシュ）
- 商品マスター（商品ID、名前、価格、在庫数）
- 注文テーブル（注文ID、ユーザーID、合計金額）
- 注文明細テーブル（注文ID、商品ID、数量）
→ トランザクション必須、在庫管理の整合性が重要

Redis (KVS)
- セッション管理（ログイン状態）
- 商品詳細ページのキャッシュ
- 人気商品ランキング（リアルタイム更新）
→ 超高速アクセスが必要

MongoDB (ドキュメント)
- 商品レビュー（星評価、コメント、画像URLなど柔軟な構造）
- 閲覧履歴（ユーザーがどの商品を見たか）
→ スキーマが流動的、大量データ

Elasticsearch (全文検索エンジン)
- 商品検索（キーワード検索、あいまい検索）
→ 高速な全文検索が必要

Amazon Redshift (カラム指向)
- 売上分析、顧客分析（データウェアハウス）
→ 大量データの集計
```

**それぞれの役割分担:**<br>
- **RDB**: 整合性が重要な業務データ（マスター、トランザクション）<br>
- **Redis**: 高速アクセスが必要な一時データ（キャッシュ、セッション）<br>
- **MongoDB**: 柔軟な構造のデータ（ログ、レビュー）<br>
- **Elasticsearch**: 検索専用<br>
- **Redshift**: 分析専用（夜間バッチで集計）<br>

## NoSQLのメリット・デメリット

### メリット

**1. 水平スケーラビリティ**<br>
複数サーバーに分散しやすい。サーバー追加で処理能力を増やせる。<br>

**2. 柔軟なスキーマ**<br>
スキーマレスなので、データ構造の変更が容易。開発スピードが上がる。<br>

**3. 高いパフォーマンス**<br>
特定用途（KVSの読み書き、カラム指向の集計など）で超高速。<br>

**4. 大量データに強い**<br>
ペタバイト級のデータでも分散処理で対応可能。<br>

### デメリット

**1. トランザクションが弱い**<br>
複数ドキュメント間のACIDトランザクションが難しい（製品により改善中）。<br>

**2. クエリ言語が統一されていない**<br>
SQLのような標準がなく、製品ごとに学習コストが高い。<br>

**3. JOINができない（または遅い）**<br>
複数のコレクション（テーブル相当）を結合するのが苦手。<br>

**4. 運用ノウハウが少ない**<br>
RDBに比べて歴史が浅く、トラブル時の情報が少ない場合がある。<br>

**5. 結果整合性（Eventually Consistent）**<br>
データの整合性が「最終的に」保証される設計が多い。リアルタイムで完全一致しない場合がある。<br>

## まとめ

**NoSQLはRDBの代替ではなく、補完的な存在。**<br>

| 選択基準 | RDB | NoSQL |
|---------|-----|-------|
| データの整合性 | 絶対必要 → RDB | 多少のズレOK → NoSQL |
| データ量 | 〜数百GB → RDB | TB〜PB級 → NoSQL |
| スケール方向 | 1台で十分 → RDB | 分散必須 → NoSQL |
| スキーマ | 固定 → RDB | 流動的 → NoSQL |
| クエリの複雑さ | 複雑なJOIN → RDB | シンプルな取得 → NoSQL |

**実務での推奨アプローチ:**<br>
1. **基本はRDB**（PostgreSQL、MySQL）から始める<br>
2. パフォーマンスのボトルネック（遅い部分）が明確になったら、**部分的にNoSQLを導入**<br>
3. 適材適所で組み合わせる（RDB + Redis + MongoDBなど）<br>

**NoSQLを選ぶ明確な理由がない限り、RDBを使うのが無難。**<br>
「なんとなくモダン」「スケールするかも」という理由でNoSQLを選ぶと、後で複雑さに悩まされることが多い。<br>

まずはRDBで作り、実際に問題が起きたタイミングで最適なNoSQLを検討するのが現実的。<br>
